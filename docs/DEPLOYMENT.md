# Публикация

Как «Сёрчь» попадает к людям: что собирается, чем это проверяется,
куда уезжает и что нужно нажать руками один раз.

Файл описывает то, что есть в репозитории сегодня. Про то, чего пока нет,
здесь так и написано — «этого пока нет».

---

## Коротко: что сейчас есть, а чего нет

**Есть** способ показать продукт одной ссылкой: сайт и кабинет собираются
в один каталог и уезжают на GitHub Pages тремя командами. Это демонстрация —
кабинет работает на встроенных данных, без сервера.

**Пока нет:**

- боевого развёртывания. В корневом `README.md` записано решением проекта:
  «Деплой: не настраивается. Разработка локальная; DigitalOcean-путь шаблона
  (`.do/`, `bun run deploy:do:specs`) остаётся нетронутым до отдельного решения»;
- подключённого бэкенда. Сборка демонстрации собирает только `website` и
  `webapp` (см. `scripts/build-demo.mjs`, строки 109–110). Папка `backend`
  в неё не входит, сервер нигде не поднимается;
- автоматической публикации. Каталога `.github/` в репозитории нет,
  ни один робот сборку не запускает — все три команды запускает человек;
- самой опубликованной демонстрации. На `origin`
  (`github.com/nikitakozyr51-wq/serch-demo`) сегодня есть только ветка `main`.
  Ветки `gh-pages` там ещё нет, то есть выкладка ни разу не проходила.

## 1. Одна ссылка, а не две

Сайт (`website`, Astro) и кабинет (`webapp`, React) — два разных приложения,
и собираются они по отдельности. Но человеку, которому показывают продукт,
нельзя давать две ссылки: он читает про сервис, жмёт «Создать агентство» —
и должен оказаться в кабинете, не меняя адрес в браузере.

Поэтому сборка складывает их в один каталог:

```
.demo/
  index.html        лендинг и все страницы сайта — на корне
  pricing/ law/ blog/ …
  404.html
  app/              кабинет целиком — во вложенной папке
    index.html
    404.html        копия страницы «не найдено», см. раздел 4
  .nojekyll
  .serch-demo-build метка сборки, см. раздел 2
```

Адрес кабинета — `<корень>/app/`.

## 2. Три шага: собрать, проверить, выложить

Команды взяты из корневого `package.json` (раздел `scripts`).

### Шаг 1. Собрать

| Команда | Что делает |
| --- | --- |
| `bun run demo` | `node scripts/build-demo.mjs` — сборка для своего домена (корень пустой) |
| `bun run demo:pages` | `node scripts/build-demo.mjs serch-demo` — сборка для GitHub Pages |

`scripts/build-demo.mjs` по шагам:

1. Проверяет аргумент. Если имя папки начали со слэша — останавливается
   и объясняет почему (раздел 3).
2. Запускает `bun run build` сначала в `website`, потом в `webapp`, передав
   каждой сборке переменную `SERCH_BASE`. Если любая из двух сборок падает,
   скрипт останавливается с её кодом возврата и дальше не идёт.
3. Забирает каталог `.demo` под себя — но только доказав, что каталог его
   (раздел 2 ниже про метку).
4. Копирует `website/dist` в `.demo`, а `webapp/dist` — в `.demo/app`.
5. Кладёт пустой файл `.nojekyll`. Без него GitHub Pages прогонит каталог
   через Jekyll и выбросит всё, что начинается с подчёркивания, — а Astro
   складывает свои файлы именно в `_astro`. Сайт при этом развалится
   молча, без единой ошибки в логах.
6. Копирует `404.html` ещё и в `app/404.html` (раздел 4).
7. Печатает, сколько получилось HTML-страниц, по какому адресу кабинет
   и какой командой это проверить.

### Шаг 2. Проверить

```
bun run demo:check      →  node scripts/check-demo.mjs serch-demo
```

Если собирали командой `bun run demo` (без корня), проверять надо тоже
без аргумента: `node scripts/check-demo.mjs`. Корень при сборке и при проверке
должен совпадать, иначе проверка будет стучаться не по тем адресам.

**Зачем отдельная проверка.** В комментарии самого скрипта записан случай,
который её и породил: восемь адресов из одиннадцати отдавали «страницы нет»,
а сборка, проверка типов и тесты при этом молчали. Для сборщика мёртвая
ссылка — не ошибка.

`scripts/check-demo.mjs` поднимает на порту 4407 маленький сервер,
который ведёт себя как GitHub Pages: есть файл — отдаёт файл, нет файла —
отдаёт ближайший `404.html` и код 404. Затем открывает браузер Chromium
(окно 1440×1024) и смотрит четыре вещи:

1. **Страницы сайта.** Список из 15 адресов зашит в скрипте (`SITE_PAGES`):
   главная, тарифы, «как это работает», право, о компании, контакты, оферта,
   политика, согласие, блог и одна статья, статус, отказ от звонков,
   удаление данных, подтверждение номера. Каждая обязана ответить кодом 200
   и содержать тег `<main>` — то есть быть страницей, а не заглушкой.
2. **Кабинет открывается.** По адресу `/app/` скрипт ждёт до 10 секунд
   появления любого элемента с атрибутом `data-slot`. Не дождался — значит,
   вместо интерфейса белый лист.
3. **Глубокая ссылка работает.** Открывает `/app/login` и убеждается,
   что человек остался внутри `/app/` и интерфейс нарисовался (раздел 4).
4. **Ссылки не ведут мимо корня.** На главной собираются все ссылки,
   начинающиеся со слэша; каждая, которая не начинается с корня сборки, —
   ошибка. Эта проверка включается, только когда корень задан.

Заодно скрипт ловит ошибки JavaScript в кабинете и показывает первую из них.

Если хоть что-то не прошло, в конце печатается список с крестиками,
и скрипт завершается кодом 1.

Проверке нужен браузер Chromium. Если он на машине не установлен, его ставит
команда `bun run --cwd webapp e2e:install`.

### Шаг 3. Выложить

```
bun run demo:publish    →  node scripts/publish-demo.mjs
```

Скрипт сначала проверяет содержимое сборки (раздел 6), потом отправляет её
в отдельную ветку `gh-pages` (раздел 5) и в конце печатает готовые адреса:

```
Сайт:    https://nikitakozyr51-wq.github.io/serch-demo/
Кабинет: https://nikitakozyr51-wq.github.io/serch-demo/app/
```

**Порядок обязателен.** `demo:publish` не собирает и не проверяет — он берёт
то, что лежит в `.demo`, и отправляет. Если пропустить шаг 1, скрипт скажет
«Сборки нет». Если пропустить шаг 2, он этого не заметит и выложит нерабочее.

## 3. Почему сборка идёт в `.demo/`, а не в `docs/`

GitHub Pages умеет отдавать сайт из корня ветки или из папки `docs` —
и это прямо подталкивает положить сборку в `docs/`. Так и было сделано.
Первая же сборка стёрла документацию проекта: папка `docs/` была занята,
в ней жили ARCHITECTURE, DEPLOYMENT, TESTING и остальные файлы. В git они
не были добавлены, и вернуть их не удалось. Файл, который вы читаете, —
новый; прежний текст восстановлению не подлежал.

Из этого сделаны два вывода, и оба записаны в коде.

**Первый: результат идёт в `.demo/`.** Этот каталог создаёт сборка, и никто
кроме неё туда ничего не кладёт. В `.gitignore` он перечислен вместе с
`.demo-publish/` — собранные файлы не должны попадать в историю кода,
иначе каждый коммит с правкой одной строки тащил бы за собой пересобранный
сайт целиком.

**Второй: скрипт обязан доказать, что каталог его.** В `build-demo.mjs`
есть функция `claim`, и она работает так:

- каталога нет — создаём и кладём внутрь метку;
- каталог есть и пуст — кладём метку;
- каталог есть, не пуст, и в нём лежит метка `.serch-demo-build` — это наша
  прошлая сборка, её можно стереть целиком и собрать заново;
- каталог есть, не пуст, метки нет — **остановиться и ничего не удалять.**

В последнем случае скрипт печатает:

> Каталог … не пуст и не помечен как сборка демонстрации.
> Скрипт остановился, ничего не удалив: в этой папке может лежать чужая работа.
> Если каталог действительно можно стереть — удалите его руками и запустите снова.

Метка — обычный текстовый файл `.serch-demo-build` со строкой
«сборка демонстрации, каталог создан скриптом». Смысл правила простой:
скрипт, который стирает каталог целиком, обязан сначала доказать, что этот
каталог принадлежит ему. Один раз отсутствие такого доказательства уже стоило
проекту документации.

## 4. Базовый путь: `SERCH_BASE` и `SERCH_APP_BASE`

**Что такое базовый путь.** Это то, с чего начинаются все внутренние адреса
сайта. На своём домене сайт лежит на корне: `serch.ru/pricing`. На GitHub Pages
для проекта корень не пустой — он равен имени репозитория:
`nikitakozyr51-wq.github.io/serch-demo/pricing`. Все ссылки на страницы,
скрипты, шрифты и картинки должны получить эту приставку, иначе браузер
пойдёт за ними не туда.

### `SERCH_BASE` — корень сайта

Переменную читают обе конфигурации сборки:

- `website/astro.config.mjs`: `const base = process.env.SERCH_BASE || undefined`
  — Astro сам подставляет её во все внутренние ссылки;
- `webapp/vite.config.ts`: `const siteBase = process.env.SERCH_BASE ?? ''`.

Устанавливает её сам `build-demo.mjs`, передавая обеим сборкам
(`env: { ...process.env, SERCH_BASE: base }`). Руками её выставлять не нужно.

### `SERCH_APP_BASE` — корень кабинета

В `webapp/vite.config.ts` путь кабинета собирается из двух переменных:

```
const appBase = process.env.SERCH_APP_BASE ?? `${siteBase}/app/`
```

То есть по умолчанию кабинет живёт в папке `app` внутри корня сайта.
`SERCH_APP_BASE` позволяет это переопределить целиком, и в репозитории она
используется ровно в одном месте — в `webapp/playwright.design.config.ts`,
где полосе сверки с макетом задано `SERCH_APP_BASE: '/'`.

Причина такая: проверки дизайна пишут адреса продукта — `/today`, `/search`,
`/m/today`, — и это правильно, папка на хостинге к макету отношения не имеет.
Дописать папку в настройку `baseURL` у Playwright нельзя технически: адрес,
начинающийся со слэша, затирает путь целиком, и `/app/` вместе с `/today`
даёт `/today`. Поэтому папку убирает сервер, а не проверка.

### Почему имя папки передаётся без ведущего слэша

Правильно:

```
node scripts/build-demo.mjs serch-demo
```

Неправильно:

```
node scripts/build-demo.mjs /serch-demo
```

**Что происходит со слэшем.** Git Bash на Windows принимает любой аргумент,
начинающийся со слэша, за путь файловой системы и молча переписывает его —
`/serch-demo` превращается в `C:/Program Files/Git/serch-demo`. Это не ошибка
и не предупреждение, это тихая подмена.

**Что ломается.** Сборка проходит успешно. Зелёная. Но собран сайт с корнем,
которого не существует: все ссылки на скрипты и стили ведут в
`C:/Program Files/Git/serch-demo/...`. Обнаружится это только на хостинге —
белой страницей. Человек открывает ссылку, видит пустоту, и единственный след
проблемы — коды 404 в консоли браузера, куда он не полезет.

**Как это закрыто.** `build-demo.mjs` первым делом отказывается принимать
аргумент со слэшем:

> Имя папки передаётся без ведущего слэша: node scripts/build-demo.mjs serch-demo
> Со слэшем Git Bash подменит его на путь к своей установке, и сайт соберётся
> с чужим корнем.

Слэш добавляется внутри скрипта: `base = '/' + raw`. Снаружи его писать не надо
никогда. То же и у проверки — `check-demo.mjs` слэши по краям аргумента срезает.

## 5. Глубокие ссылки в кабинет и зачем нужен `404.html`

**В чём сложность.** Сайт — это набор настоящих файлов: адресу `/pricing`
на диске соответствует `pricing/index.html`. Кабинет устроен иначе: это
одностраничное приложение, на диске лежит один-единственный `app/index.html`,
а все экраны — `/app/today`, `/app/search`, `/app/login` — рисует браузер
уже после загрузки.

Статический хостинг об этом не знает. На запрос `/app/search` он ищет файл
с таким путём, не находит и честно отдаёт «страницы нет». Так ломаются все
ссылки, присланные кому-то напрямую, и так же ломается перезагрузка
страницы (F5) внутри кабинета.

**Как это решено — цепочка из трёх файлов.**

1. **`website/src/pages/404.astro`.** Astro берёт страницу для несуществующего
   адреса только отсюда — имя файла задано фреймворком. Внизу страницы стоит
   встроенный скрипт: если адрес начинается с `<корень>/app/` и не равен ему,
   человека перебрасывает обратно в кабинет, а адрес, куда он шёл,
   передаётся параметром:

   ```
   /serch-demo/app/search  →  /serch-demo/app/?p=%2Fsearch
   ```

   Обычные адреса сайта этим не затронуты: условие срабатывает только внутри
   `/app/`. Человек, опечатавшийся в адресе страницы сайта, видит нормальную
   страницу «Такой страницы нет» с панелью «куда можно пойти», а не прыжок
   в кабинет.

2. **`scripts/build-demo.mjs`** копирует `404.html` ещё и в `app/404.html`.
   Хостинг ищет страницу «не найдено» рядом с запрошенным путём; без этой
   копии `/app/search` упёрся бы в стандартную страницу GitHub, а не в нашу.

3. **`webapp/src/main.tsx`** забирает адрес обратно:

   ```
   const redirected = new URLSearchParams(window.location.search).get('p')
   if (redirected) {
     const base = import.meta.env.BASE_URL.replace(/\/+$/, '')
     window.history.replaceState(null, '', base + redirected)
   }
   ```

   Это происходит **до** того, как маршрутизатор посмотрит на адрес, — иначе
   кабинет открылся бы на «Сегодня» вместо нужного экрана. Используется
   `replaceState`, а не переход: в истории браузера не должно остаться
   технической ссылки с параметром `?p=`, иначе кнопка «назад» вернула бы
   на неё же.

Для человека всё это невидимо: он открывает присланную ссылку и попадает
на нужный экран. Работоспособность цепочки проверяет `check-demo.mjs`
адресом `/app/login` — см. шаг 2.

## 6. Ветка `gh-pages` и настройка GitHub Pages

**Почему отдельная ветка.** Собранные файлы не попадают в `main`. Они уезжают
в ветку `gh-pages`, где нет ничего, кроме самой демонстрации. Иначе каждый
коммит с правкой одной строки тащил бы за собой пересобранные скрипты,
и история кода превратилась бы в историю сборок.

**Как это делает `publish-demo.mjs`.** Скрипт не переключает вашу рабочую
ветку — он создаёт рядом отдельную рабочую копию (`git worktree`) в каталоге
`.demo-publish`, и всё делает там:

- если ветка `gh-pages` уже есть на сервере — берёт её;
- если ветки нет — создаёт пустую, без общей истории с `main` (`--orphan`);
- очищает содержимое целиком и копирует туда свежую сборку. Демонстрация
  всегда целая, а не смесь нового с забытым старым;
- если после копирования ничего не изменилось, сообщает «Изменений нет:
  на ветке уже эта сборка» и не делает пустой коммит;
- иначе коммитит с сообщением вида `демонстрация: сборка 2026-08-05 17:16`
  и отправляет в `origin`;
- в конце убирает временную рабочую копию.

Если у репозитория нет `origin`, скрипт останавливается: публиковать некуда.

**Что нужно нажать руками — один раз.** GitHub сам не догадается отдавать
сайт из новой ветки. После первой отправки надо зайти в настройки репозитория:

> **Settings → Pages → Source: Deploy from a branch → Branch: `gh-pages`, папка `/` (root) → Save**

Скрипт печатает прямую ссылку на эту страницу настроек в конце работы.
Повторять не нужно — дальше каждая новая отправка подхватывается сама,
обычно за минуту-другую.

Сегодня на `origin` ветки `gh-pages` нет, то есть этот шаг ещё предстоит.

## 7. Что `publish-demo.mjs` проверяет до отправки и почему

**Почему проверка стоит именно здесь.** Отправка в открытый репозиторий
необратима. Git помнит всё: удаление файла следующим коммитом не убирает его
из истории — файл остаётся доступен по прежнему адресу навсегда. Значит,
единственный момент, когда ошибку ещё можно остановить, — до отправки.

### Проверка первая: в сборке нет лишних файлов

Скрипт обходит все файлы в `.demo` и останавливается, если находит хоть что-то
из этого списка:

| Что | Почему нельзя |
| --- | --- |
| `*.xlsx`, `*.xls` | Рабочие выгрузки по собственникам. Это персональные данные живых людей |
| `*.pen` | Дизайн-файл |
| папка `.private/` | Всё, что получено из рабочих выгрузок |
| файл или папка `serch` | Дизайн-файл проекта в Pencil — он лежит в корне репозитория под именем `serch` и весит около 8 МБ |

Те же `*.xlsx`, `*.xls` и `.private/` перечислены в `.gitignore` — то есть
защита двойная: они не попадают в git вообще и отдельно проверяются перед
публикацией. Файл `serch` в `.gitignore` не перечислен: он просто не добавлен
в git, и от попадания в демонстрацию его страхует только эта проверка.

При находке печатается список найденного, и скрипт завершается кодом 1.
Ничего не отправляется.

### Проверка вторая: телефоны вне выдуманного диапазона

Это отдельная проверка, и она важнее остальных.

Настоящие номера в открытой демонстрации недопустимы: это персональные данные
живых людей, а продукт прямо обещает их не публиковать. До того как это было
исправлено, на лендинге и в кабинете стояли номера в кодах 911, 921 и 981 —
настоящие петербургские диапазоны МТС и МегаФона. Каждый такой номер прямо
сейчас может быть чьим-то, и публичная страница с ним — это чужой телефон,
выложенный в интернет.

Официального «диапазона для примеров», как британский `07700 900xxx`,
в России нет. Поэтому проект выбрал форму, которая читается как телефон,
но абоненту выдана быть не может (`webapp/src/lib/demo-phone.ts`):

```
+7 900 000-XX-XX
```

Абонентские блоки внутри кода DEF операторам выделяются не с нуля, и номер
с тремя нулями в начале абонентской части ни на что не похож, кроме образца.
Рядом стоит второе правило, которое и даёт настоящую гарантию: **ни один
телефон в демонстрации не является ссылкой `tel:`** — номер можно прочитать
и скопировать, но нельзя позвонить одним нажатием.

`publish-demo.mjs` читает все файлы `.html`, `.js`, `.json` и `.css` в сборке,
ищет в них любой российский мобильный номер и оставляет без внимания только
те, что начинаются с `+7 900 000-`. Всё остальное собирается в список,
печатается, и скрипт останавливается:

> В сборке найдены телефоны вне выдуманного диапазона: …
> Остановился. Публиковать чужие номера нельзя.

Если обе проверки прошли, скрипт печатает, сколько файлов в сборке, и
переходит к отправке.

## 8. Заготовки DigitalOcean в `.do/`

В репозитории лежат три файла:

- `.do/backend-app.yaml.example` — бэкенд: контейнер по `backend/Dockerfile`,
  порт 8080, проверка живости по адресу `/health/ready`, рядом управляемая
  база PostgreSQL 18;
- `.do/webapp-static-app.yaml.example` — кабинет как статический сайт,
  сборка командой `bun run build:webapp`, результат из `webapp/dist`;
- `.do/website-static-app.yaml.example` — сайт как статический сайт,
  сборка командой `bun run build:website`, результат из `website/dist`.

**Это заготовки, а не настройки.** Все значения в них — заглушки вида
`REPLACE_WITH_PROJECT_SLUG`, `REPLACE_WITH_GITHUB_REPO`,
`REPLACE_WITH_DO_APP_REGION`. Как есть они не работают. Готовые описания
из них делает команда

```
bun run deploy:do:specs     →  bun scripts/prepare-do-specs.mjs
```

Результат она кладёт в `.scratch/deploy` — каталог, который в git не попадает
(`.scratch/` перечислен в `.gitignore`). Так сделано намеренно: в готовых
описаниях появляются адреса и секреты, и им нечего делать в истории кода.

**Сейчас этот путь не используется.** Решение проекта в `README.md`: деплой
не настраивается, DigitalOcean-путь шаблона остаётся нетронутым до отдельного
решения. Демонстрация выкладывается скриптами `demo:*` на GitHub Pages —
это совсем другой механизм, и он ни одной строки из `.do/` не читает.

**Чем боевой путь отличается от демонстрации,** если до него дойдёт дело:

- глубокие ссылки в кабинет там решаются иначе. У DigitalOcean в описании
  кабинета стоит `catchall_document: index.html` — хостинг сам отдаёт
  главный файл приложения на любой неизвестный адрес, и обходной путь
  через `404.html` (раздел 5) не нужен;
- адрес бэкенда передаётся кабинету переменной времени сборки `VITE_API_URL`,
  а сайту — `PUBLIC_WEBSITE_URL`. В демонстрации ни та, ни другая не задаются:
  бэкенд к продукту не подключён, и кабинет работает на встроенных данных;
- бэкенд разворачивается как контейнер с базой, а не как набор файлов.

Конкретные машинные умолчания для DigitalOcean живут в
`scripts/prepare-do-specs.mjs`; при их изменении этот файл нужно править
вместе со скриптом.

## 9. Частые вопросы

**Открыл ссылку — белая страница.** Почти всегда это ошибка в корне: сборка
шла с одним корнем, а сайт лежит по другому адресу. Проверьте, что собирали
командой `bun run demo:pages` (корень `serch-demo`), а не `bun run demo`,
и что имя папки не было передано со слэшем.

**Открыл ссылку — страница GitHub «404».** Скорее всего, не сделан
однократный шаг из раздела 6: Pages не включён на ветке `gh-pages`.

**Часть страниц открывается, часть нет.** Это ровно тот случай, ради которого
написан `check-demo.mjs`. Запустите `bun run demo:check` — он назовёт
конкретные адреса.

**Правки не видно на сайте.** Публикация не пересобирает: `demo:publish`
отправляет то, что лежит в `.demo`. Пересоберите (`bun run demo:pages`),
проверьте (`bun run demo:check`), потом отправляйте.

**Скрипт отказался стирать `.demo`.** Значит, в каталоге лежит что-то, чего
сборка туда не клала, и метки `.serch-demo-build` нет. Посмотрите, что там,
удалите каталог руками и запустите снова (раздел 3).
