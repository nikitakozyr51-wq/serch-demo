# Данные и приватность

Этот файл отвечает на два вопроса: **откуда берутся числа, адреса и телефоны,
которые видно на экранах «Сёрчи»**, и **что сделано, чтобы личные данные живых
людей туда не попали**.

Файл переписан заново 5 августа 2026 года. Прежний текст утрачен: скрипт сборки
стёр папку `docs/` целиком, а файлы не были в git и не восстановились. История
записана прямо в коде — `scripts/build-demo.mjs:20-33`. Там же живёт защита,
поставленная после этого случая: скрипт отказывается удалять каталог, если
в нём есть что-то, кроме его собственной прошлой сборки
(`scripts/build-demo.mjs:60-92`). Сборка теперь кладётся в `.demo/`, а не в `docs/`,
поэтому эта папка снова безопасна.

---

## Главное, что нужно понимать про сегодняшнее состояние

**Бэкенд не подключён к продукту.** Сервер в репозитории есть — папка `backend/`,
но в его схеме базы (`backend/prisma/schema.prisma`) заведены только пользователи,
сессии входа, подписки и push-уведомления: это модели, доставшиеся от шаблона.
Ни объекта недвижимости, ни собственника, ни телефона там нет. Продуктовые модули
бэкенда — `auth`, `billing`, `notifications`, `users` — тоже шаблонные.

Кабинет работает без сервера. Прямо об этом написано в
`webapp/src/features/auth/demo-session.ts:6-19`: человек открывает ссылку, создаёт
агентство, заходит и работает, но всё введённое остаётся в его собственном браузере
(`localStorage`) и никуда не уходит. Ни одна форма ничего не отправляет.

Отсюда следует простое: **всё, что видно на экранах, — это либо файл, лежащий
в репозитории, либо запись в браузере зрителя.** Настоящих собственников
в демонстрации нет.

### Четыре источника данных, и больше никаких

| Где лежит | Что это | Кто главный |
|---|---|---|
| `DEMO-DATA.md` в корне | документ-первоисточник: все числа, имена, адреса | закон для данных |
| `webapp/src/data/listings.ts` | 251 объект, собранный скриптом | собирается только скриптом |
| `webapp/src/data/search-rows.ts` | девять строк, снятых с макета, плюс сборка всей базы в строки выдачи | закон для внешнего вида строки |
| `webapp/src/features/auth/demo-session.ts` | сеанс зрителя: имя, агентство, баланс, что уже раскрыто | живёт в браузере, не в репозитории |

Пятый источник — рабочая база собственников в `.private/` — **в продукт не входит
вообще**. О ней отдельный раздел ниже.

Мобильное приложение (`mobile/`) продуктовых данных не содержит: ни списка объектов,
ни телефонов там нет.

## 1. Демонстрационный набор объектов: 251 штука

### Что это за файлы

Два файла и одна команда:

- `scripts/generate-listings.mjs` — скрипт, который собирает набор;
- `webapp/src/data/listings.ts` — результат его работы, лежащий в репозитории;
- `bun run listings:generate` — команда запуска (под ней выполняется
  `node scripts/generate-listings.mjs`, `package.json:45`).

Правило записано в шапке самого результата (`webapp/src/data/listings.ts:4`):
**файл собран скриптом и правится только им.** Руками в него не пишут — иначе
следующий запуск скрипта затрёт правку и никто этого не заметит.

### Почему скрипт, а не написанный руками список

Ответ в шапке скрипта (`scripts/generate-listings.mjs:4-8`): двести пятьдесят
объектов руками не написать так, чтобы медианы районов сошлись с теми, что уже
напечатаны на лендинге. А они обязаны сойтись — об этом весь раздел ниже.

### Числа не случайные, хотя и «сгенерированы»

Скрипт использует генератор псевдослучайных чисел с постоянным зерном 24072026
(`scripts/generate-listings.mjs:26-38`). Практический смысл для владельца:
**одинаковый запуск даёт одинаковый результат.** Набор не «дрожит» от запуска
к запуску, поэтому его кладут в репозиторий готовым файлом, а скрипт нужен только
чтобы пересобрать набор, когда появятся настоящие данные.

### Как считаются цены

Порядок такой (`scripts/generate-listings.mjs:290-337`):

1. **Район выбирает медиану.** У каждого из шести районов записана медиана ₽/м² —
   ровно та, что стоит в таблице лендинга: Петроградский 412 тыс, Центральный
   389 тыс, Василеостровский 271 тыс, Московский 246 тыс, Приморский 218 тыс,
   Калининский 205 тыс (`scripts/generate-listings.mjs:49-189`).
2. **Комнатность задаёт площадь.** Однокомнатная 32–45 м², двухкомнатная 50–68,
   трёхкомнатная 65–92, четырёхкомнатная 95–130 (строки 200-205). Доли
   комнатности: 32 % однушек, 38 % двушек, 24 % трёшек, 6 % четырёхкомнатных
   (строки 208-213).
3. **Цена метра — это медиана района плюс разброс** от −22 % до +26 %
   (строка 302). Разброс и есть то, ради чего колонка «отклонение от рынка»
   вообще существует: если бы все объекты стояли на медиане, искать было бы нечего.
4. **Цена объекта = цена метра × площадь**, округлённая до сотни тысяч рублей
   (строка 304), и подписывается в формате продукта — «8,6 млн ₽» (строки 266-269).
5. **Отклонение** считается от медианы своего района в целых процентах
   (строки 245-247). Мёртвая зона ±5 %: внутри неё продукт пишет «≈ рынок»,
   потому что разница в четыре процента о цене ничего не говорит.

Как это выглядит на готовом наборе: 65 объектов из 251 попадают в мёртвую зону
±5 % и читаются как «≈ рынок», крайние отклонения — −25 % и +28 %.

### Признак собственника считается, а не назначается

Значок «Сильные / Средние / Слабые» не бросок монеты
(`scripts/generate-listings.mjs:233-237`):

- одна публикация с одним номером → **Сильные**;
- две-три публикации с одним номером → **Средние**;
- больше публикаций либо несколько номеров → **Слабые**.

Это те же правила, что показаны в самом продукте и записаны в `DEMO-DATA.md:116-120`.
Если бы значок ставился случайно, он противоречил бы числам, стоящим рядом с ним
в той же строке.

### Подгонка медиан под таблицу лендинга — и что сломается, если её убрать

Это самое важное место скрипта (`scripts/generate-listings.mjs:340-364`).

**Что происходит.** После того как все объекты собраны, скрипт считает медиану
получившегося набора по каждому району, сравнивает с обещанной и домножает цены
района на отношение «обещанная медиана к получившейся». Разброс объектов между
собой при этом сохраняется, а середина встаёт ровно туда, где её обещал лендинг.

**Зачем.** Без этого шага медиана набора уходила от обещанной на 1–5 %. Разброс
цен случайный, и на полусотне объектов середина сама собой в точку не попадает.

**Чем это грозит.** Пять процентов — это ровно ширина мёртвой зоны отклонения.
То есть ошибка такого размера способна перекрасить у объекта колонку «≈ рынок»
в «▲ +6 %». Дальше цепочка простая:

- сайт печатает «Калининский, медиана 205 тыс ₽/м²» (`DEMO-DATA.md:42`);
- кабинет открывает выдачу по Калининскому, а середина в ней другая;
- значит, **продукт врёт на собственной витрине** — и это видно любому, кто
  положит два экрана рядом. Продукт, который продаёт достоверность данных,
  на такой мелочи теряет ровно то, чем торгует.

Поэтому в скрипте есть и проверка: после подгонки он печатает по каждому району
медиану, обещанное число и расхождение (`scripts/generate-listings.mjs:368-380`).

**Сверка на сегодняшнем файле** (замерено чтением `webapp/src/data/listings.ts`,
без запуска генератора):

| Район | Объектов | Медиана в наборе | Обещано лендингом |
|---|---|---|---|
| Приморский | 58 | 218 000 | 218 000 ✓ |
| Калининский | 51 | 205 000 | 205 000 ✓ |
| Московский | 50 | 246 000 | 246 000 ✓ |
| Центральный | 35 | 389 000 | 389 000 ✓ |
| Василеостровский | 31 | 271 000 | 271 000 ✓ |
| Петроградский | 26 | 412 000 | 412 000 ✓ |

Все шесть сходятся.

### Почему 251, а не 250

В скрипте написано `TOTAL = 250` (`scripts/generate-listings.mjs:194`), а в файле
лежит 251 объект. Это не ошибка и не описка: объекты раскладываются по районам
пропорционально числам из таблицы лендинга (334, 291, 286, 203, 176, 148),
и каждая доля округляется отдельно. Сумма округлений даёт 58 + 51 + 50 + 35 + 31 + 26 = 251.
Число 251 напечатано в шапке результата, потому что скрипт подставляет туда
фактическую длину набора, а не задуманную.

Мелкая техническая честность: «медиана» здесь — средний элемент списка по порядку;
при чётном числе объектов берётся верхний из двух средних, а не их полусумма.
На числах таблицы выше это ни на что не влияет, но знать это стоит, если однажды
цифры разойдутся на единицу.

### Телефонов в этом файле нет

Ни одного. У объекта есть поле `phones`, но это **количество** номеров
(один или два) — признак, из которого считается сила собственника, а не сам номер.
Полный список полей: адрес, район, метро, время пешком, комнатность, площадь,
этаж и этажность, цена, ₽/м², подпись цены, отклонение, свежесть, число публикаций
и площадок, площадка, число номеров, признак.

## 2. Девять замеренных строк живут отдельно от базы

Файл `webapp/src/data/search-rows.ts` устроен из двух частей, и это сделано
намеренно (объяснение — в его шапке, строки 5-21).

**`MEASURED_ROWS` — девять строк, снятых с макета до последнего слова**
(строка 58 и далее). Это не данные, а образцы. Девять строк несут все восемь
состояний объекта разом: в работе, стоп-лист, отказ, нет телефона, контакт
отозван, прозвонен, раскрыт, новый. Такого набора в живой базе может не оказаться
неделями, а сверять экран с макетом надо каждый день. Поэтому они стоят отдельно
и **не генерируются**: если бы они собирались вместе со всеми, снимок для сверки
менялся бы каждый раз, когда в базе появляется новый объект, и сверять было бы
не с чем.

**`ALL_ROWS` — девять образцов плюс вся база**, 251 объект, превращённый
в строки выдачи (строка 307). Без базы поиску нечего сужать: на девяти строках
фильтр по району либо оставляет всё, либо не оставляет ничего, и проверить,
что он вообще работает, невозможно.

Итого продукт показывает 260 строк, стенд для сверки — девять.

**Состояние строки у объектов из базы тоже не случайно**
(`webapp/src/data/search-rows.ts:246-277`): объект, который висит дольше суток
и стоит заметно дешевле рынка, показан как уже кем-то взятый — потому его
и заметили первым. Свежий и дорогой не взят никем. Каждый двадцать третий —
стоп-лист (число простое, чтобы отметки не выстраивались в узор рядом с другими
признаками).

**Почему образцы не набраны по документу.** Это отдельный урок, записанный
в `CODE-ERRORS.md:430-440`: девять строк однажды набрали по `DEMO-DATA.md`, адреса
и цены совпали, а формат свежести, сокращение «2-к», этаж и площадки разошлись
во всех девяти, и одна строка получила чужой чип. Правило после этого:
**макет — закон для внешнего вида, документ — закон для чисел**; если они
расходятся, подтягивают документ, а не рисуют по документу.

## 3. Телефоны

### Что было и что стало

До правки на лендинге и в кабинете стояли десять номеров в кодах **911, 921 и 981**.
Это настоящие петербургские диапазоны МТС и МегаФона, и каждый такой номер прямо
сейчас может быть чьим-то. Публичная страница с ним — это чужой телефон,
выложенный в интернет, и звонок от любопытного зрителя живому человеку
(`webapp/src/lib/demo-phone.ts:4-9`).

Сейчас все номера в продукте имеют вид:

```
+7 900 000-XX-XX
```

### Почему выбран именно такой вид

Официального «диапазона для примеров», как британский `07700 900xxx`, в России
нет. Поэтому взята форма, которая читается как телефон, но не похожа ни на что,
кроме образца: абонентские блоки внутри кода DEF операторам выделяются не с нуля,
и номер с тремя нулями в начале абонентской части ни на что не похож, кроме
примера (`webapp/src/lib/demo-phone.ts:11-19`).

### Полной гарантии это не даёт, и так прямо написано

В коде сказано без смягчений: **полной гарантии без реестра Роскомнадзора
не даёт никто** (`webapp/src/lib/demo-phone.ts:19-20`). Поэтому рядом стоит второе
правило, которое гарантию и обеспечивает.

### Правило: ни один телефон не является ссылкой `tel:`

Номер в демонстрации можно прочитать и скопировать, но **нельзя позвонить одним
нажатием** (`webapp/src/lib/demo-phone.ts:22-24`). Случайного звонка не будет даже
при самом неудачном совпадении: чтобы позвонить, зрителю придётся набрать номер
руками и осознанно.

Правило соблюдается: в исходниках `webapp/src`, `website/src` и `mobile`
нет ни одной ссылки `tel:`. Единственное упоминание этих четырёх букв во всём
рабочем коде — сам комментарий, который правило формулирует. (Ссылки `tel:`
встречаются в исследовательских папках `design-research/` и `research/` —
это разборы чужих интерфейсов и черновики спецификаций, в продукт они не входят.)

### Скрытый номер до раскрытия

Пока контакт не оплачен, показывается `+7 900 ··· ·· 42`
(`webapp/src/lib/demo-phone.ts:55-64`): видны код и две последние цифры — ровно
столько, чтобы человек узнал свой номер, если это он, и не хватило, чтобы
позвонить. За остальное платят 199 ₽.

### Номер устойчив, а не случаен

Один и тот же ключ всегда даёт один и тот же номер
(`webapp/src/lib/demo-phone.ts:34-52`). Это нужно, чтобы объект «Ленская ул., 10»
показывал один телефон и в выдаче, и в карточке, и в прозвоне, и в журнале доступа.
Разные номера у одного собственника разваливают демонстрацию на глазах у зрителя.

### Автоматическая проверка перед публикацией

Скрипт публикации `scripts/publish-demo.mjs` не отправляет сборку, пока не проверит
её сам (строки 67-91): он читает все собранные `.html`, `.js`, `.json` и `.css`,
находит в них всё, похожее на российский мобильный номер, и **останавливается,
если хоть один номер не начинается с `+7 900 000-`**. Сообщение при остановке:
«Публиковать чужие номера нельзя».

Отправка в открытый репозиторий необратима — git помнит всё, и удаление файла
следующим коммитом не убирает его из истории (`scripts/publish-demo.mjs:20-25`).
Поэтому проверка стоит до отправки, а не после.

### Три честных разрыва, которые надо знать

1. **Функций сборки номера в коде две, а не одна.** Одна в
   `webapp/src/lib/demo-phone.ts` (даёт строго `+7 900 000-XX-XX`), вторая
   в `webapp/src/features/auth/demo-session.ts:174-181` (даёт `+7 900 AAA-BB-CC`,
   где `AAA` — любые три цифры, не обязательно нули). Вторая нарушила бы правило
   публикации, если бы попала на экран, и проверка из `publish-demo.mjs` её
   не поймала бы: номер собирается в браузере зрителя, а в файлах сборки лежит
   только шаблон. Сегодня это не срабатывает, потому что —
2. **обе функции сейчас никем не вызываются.** Ни один экран их не использует:
   номера на экранах записаны строками прямо в разметке, все в правильном
   диапазоне `+7 900 000-XX-XX` (проверено по `webapp/src` и `website/src`).
   То есть правило соблюдается, но держится на аккуратности человека, а не
   на коде.
3. **`DEMO-DATA.md` до сих пор содержит номера в настоящих диапазонах** —
   коды 911, 921 и 981, то есть выданные операторами связи и потенциально
   принадлежащие живым людям. Экраны их не показывают, и сам документ в
   публичный репозиторий не уезжает: он перечислен в `.gitignore` вместе с
   остальными внутренними материалами. Но правило «ни один номер не
   принадлежит живому человеку» на документ-первоисточник пока не
   распространено — это незакрытая работа, а не решение.

   Сами номера здесь НЕ ПЕРЕЧИСЛЕНЫ, и это тоже правило: документ о том, как
   мы не публикуем чужие телефоны, не должен публиковать чужие телефоны.
   Раньше они стояли в этом абзаце списком.

## 4. Рабочая база собственников: `.private/`

**Этот файл я не открывал.** Всё, что написано ниже, взято из описаний в самом
репозитории, а не из содержимого таблицы.

### Что это

Рабочая выгрузка, с которой агенты работают прямо сейчас: **212 объектов
по Петербургу**, снятых с Авито, Циана, Яндекса, Домклика, Юлы и частично
собранных телефонными звонками (`PROMPT-аренда-и-продажа.md:9-11`).

**Это аренда, а не продажа.** И в этом главное несовпадение с продуктом:

| | Продукт нарисован под | Рабочая база про |
|---|---|---|
| Что | продажу квартир | аренду |
| Цена | 8,6 млн ₽ | 45 000 – 180 000 ₽/мес, медиана 70 000 |

Источники: `PROMPT-аренда-и-продажа.md:17-99`, `АРЕНДА-v1.md:345-349`.

**В коде продукта аренды пока нет.** Решения по ней записаны в `АРЕНДА-v1.md`
(девять пунктов, 5 августа 2026), экраны нарисованы в дизайн-файле, но
в `webapp/src` режима «Продажа | Аренда» не существует: слово «Аренда» встречается
там только в комментарии к данным и на экране состояний.

### Почему она не попадает в публикацию

Потому что это персональные данные живых людей — имена или телефоны собственников,
которые ничего не разрешали. Причина, записанная прямо в `.gitignore`:

> Репозиторий публичный, а git помнит навсегда — один случайный коммит здесь
> нельзя отменить удалением файла.

Есть и продуктовая причина, отдельная от юридической: 212 объектов — рабочая база,
а не витрина, и показывать охват, которого нет, продукт себе позволить не может,
потому что продаёт именно достоверность (`АРЕНДА-v1.md:207-209`).

### Три замка, а не один

1. **`.gitignore`** закрывает и саму папку `.private/`, и любые файлы `.xlsx`
   и `.xls` где угодно в дереве — «и всё, что из них получено». Один замок
   на путь и один на тип файла: если таблицу однажды скопируют в другое место,
   второй замок сработает.
2. **Список запрещённого в публикации** (`scripts/publish-demo.mjs:58`): сборка
   не уедет на хостинг, если в ней найдётся `.xlsx`, `.xls`, `.pen` (дизайн-файл),
   что-либо из `.private/` или корневой файл `serch` — это Pencil-макет
   на 7,8 МБ, лежащий в корне без расширения.
3. **Телефонный фильтр** из раздела про телефоны — последняя сетка на случай,
   если данные просочатся не файлом, а текстом внутри страницы.

## 5. `DEMO-DATA.md` — почему числа обязаны сходиться

### Что это за файл

`DEMO-DATA.md` лежит в корне репозитория и называет себя единственным источником
правды. Правило на первой странице:

> Любое число на любом экране берётся отсюда. Если числа нет здесь, его нельзя
> рисовать.

В нём: одна дата «сегодня» на весь продукт (24 июля), таблица районов
с медианами, девять строк рабочего фильтра, состав агентства из пяти человек
с их показателями, деньги (199 ₽ за контакт, 3 000 ₽ в месяц за агентство),
возвраты за 30 дней поимённо, журнал раскрытий, подборки, реквизиты сервиса
и агентства-клиента, сроки и лимиты экранов входа, записи блога.

### Почему сходимость — это не педантизм

Продукт продаёт достоверность данных. Экран, который спорит с соседним экраном,
уничтожает ровно то, за что агентство платит. В самом файле записаны случаи,
когда это ломалось:

- **журнал доступа насчитывал четыре раскрытия на 796 ₽** там, где все прочие
  экраны показывали три на 597 ₽ — потому что каждая таблица печатала событие
  заново (`DEMO-DATA.md:390-404`);
- **возврат стоял раньше раскрытия**, за которое возвращён, — три пары
  с отрицательной разницей, до −19 часов (`DEMO-DATA.md:406-409`);
- **одна сущность показывала четыре разных числа**: сайдбар писал «Подборки 4»,
  экран подборок рисовал шесть, строка внутри — восемь, публичная страница
  писала словом «Восемь объектов» при шести нарисованных (`DEMO-DATA.md:368-372`);
- **дата стоп-листа была «12 сентября» при сегодняшнем 24 июля** — событие
  из будущего (`DEMO-DATA.md:190-191`).

Поэтому файл написан с проверками прямо в тексте: 630 + 419 = 1 049 снято,
1 240 − 1 049 = 191 остаётся; 9 × 199 = 1 791 ₽ возвращено; 64 + 52 + 38 + 18 + 6 = 178
раскрытий. Каждое число можно пересчитать, не выходя из документа.

### Как документ связан со сгенерированным набором

Медианы районов в `scripts/generate-listings.mjs` взяты из таблицы `DEMO-DATA.md:35-42`.
Пропорции районов (334 объекта в Приморском, 148 в Петроградском) — из той же
таблицы. Правила признака собственника — из `DEMO-DATA.md:116-120`. То есть
скрипт не выдумывает мир, а разворачивает документ в 251 строку.

### Разрыв, о котором стоит знать

`DEMO-DATA.md:131` говорит: **отклонение считается от медианы цены аналогов,
а не от медианы района** — аналог это та же комнатность в радиусе 700 м за
60 дней. `АРЕНДА-v1.md:21-26` подтверждает: медианы по районам живут только
в витринной таблице лендинга, а механизм отклонения их не использует, и попытка
считать от района уже трижды ломала макеты.

А сгенерированный набор считает отклонение **именно от медианы района**
(`scripts/generate-listings.mjs:245-247`, и это же написано в шапке
`webapp/src/data/listings.ts:15`). Девять замеренных строк при этом несут
отклонения, снятые с макета, то есть посчитанные по аналогам.

Значит, в продукте сейчас сосуществуют две базы отсчёта: у девяти образцов —
аналоги, у 251 объекта — район. На экране разницы не видно, потому что число
уже посчитано и лежит готовым. Но когда за продуктом появится настоящий расчёт,
второй способ придётся убрать: он даёт соседним домам на одной улице разные базы,
и именно этим разрывом в 14 % макеты ломались раньше.

## 6. Правило, которое не обсуждается

> **Персональные данные живых людей не попадают в открытую демонстрацию
> ни при каких условиях.**

Это не пожелание и не «хорошая практика». Это то, что продукт обещает делать
для собственников: «Сёрчь» существует, чтобы номер человека не расходился
по рукам бесконтрольно. Демонстрация, показывающая чужой телефон, опровергает
продукт быстрее, чем любой конкурент.

Из правила следует пять конкретных вещей, каждая из которых уже сделана:

1. **Ни один настоящий номер не хранится в репозитории.** Все телефоны
   на экранах — из диапазона `+7 900 000-XX-XX`.
2. **Ни один телефон не является ссылкой `tel:`.** Позвонить одним нажатием
   нельзя даже при неудачном совпадении номера.
3. **До оплаты номер показан частично** — код и две последние цифры.
4. **Рабочая база закрыта тремя замками** и не может уехать ни коммитом,
   ни сборкой.
5. **Публикация останавливается сама**, если найдёт в сборке чужой номер
   или запрещённый файл.

Чего правило **не** гарантирует, и это надо назвать честно:

- диапазон `+7 900 000-XX-XX` выбран рассуждением, а не выпиской из реестра
  Роскомнадзора; страховка здесь — запрет на `tel:`, а не сам диапазон;
- `DEMO-DATA.md` пока содержит номера в настоящих кодах 911, 921, 981
  (см. раздел 3);
- проверка перед публикацией смотрит на собранные файлы, а не на то, что
  соберётся в браузере во время работы.

Когда за продуктом появится настоящая база, правило не смягчается, а становится
строже: номера придут с сервера по одному, за деньги, с записью в журнале доступа,
и ни один из них не окажется в репозитории (`webapp/src/data/listings.ts:9-13`).

## Команды, которые относятся к данным

Ровно те, что заведены в `package.json`:

| Команда | Что делает |
|---|---|
| `bun run listings:generate` | пересобирает `webapp/src/data/listings.ts` из скрипта |
| `bun run demo` | собирает сайт и кабинет в один каталог `.demo/` |
| `bun run demo:pages` | то же, но с корнем `serch-demo` для GitHub Pages |
| `bun run demo:check` | проверяет собранную демонстрацию так, как её увидит человек по ссылке |
| `bun run demo:publish` | публикует сборку — с проверкой на чужие номера и запрещённые файлы |
| `bun run demo:dead-buttons` | ищет кнопки, которые ничего не делают |

Отдельной проверки «данные сошлись между собой» в репозитории **нет**: сходимость
чисел между экранами и `DEMO-DATA.md` сегодня держится на человеке, читающем оба
источника. Скрипт генерации печатает сверку медиан по районам, но только для себя
и только в момент запуска.

## Чего в продукте пока нет

Чтобы этот файл нельзя было прочитать как обещание:

- **сервера за продуктом нет** — ни базы объектов, ни базы собственников,
  ни оплаты, ни журнала доступа на стороне сервера;
- **режима аренды нет** в коде, хотя решения по нему записаны и экраны нарисованы;
- **автоматической сверки данных с `DEMO-DATA.md` нет**;
- **источника настоящих объявлений нет**: ни парсеров площадок, ни склейки дублей,
  ни проверки номера — механизм антидубля описан в документах и нарисован
  на экранах, но кода за ним не стоит;
- **номера в `DEMO-DATA.md` не переведены** в безопасный диапазон.
