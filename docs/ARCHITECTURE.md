# Архитектура

Документ описывает, из чего собрана «Сёрчь» и как части связаны **сегодня**.
Он написан по коду репозитория, а не по планам: если чего-то нет, здесь так
и сказано.

Прежняя версия этого файла потеряна. Причина записана в самом коде —
`scripts/build-demo.mjs`: сборка демонстрации складывалась в папку `docs/`,
а там уже жила документация, и первая же сборка стёрла её. Файлы не были
в git, вернуть не удалось. Теперь сборка кладёт результат в `.demo/`
и отказывается стирать каталог, если в нём есть хоть что-то, кроме прошлой
сборки, — проверка `claim()` в том же скрипте.

---

## 1. Из чего собран продукт

Репозиторий — **монорепозиторий**: несколько самостоятельных приложений лежат
в одной папке и собираются одним менеджером пакетов. Менеджер — `bun`, версия
закреплена в корневом `package.json` (`"packageManager": "bun@1.3.14"`).
Список частей объявлен там же, в поле `workspaces`.

| Папка | Что это | На чём написано |
|---|---|---|
| `website/` | Публичный сайт: лендинг, тарифы, правовые страницы, блог | Astro 7, React для отдельных вставок |
| `webapp/` | Кабинет агентства: рабочие экраны | React 19, Vite 8, TanStack Router |
| `backend/` | Сервер: вход, пользователи, подписки, уведомления | Hono, Prisma, PostgreSQL, работает на Bun |
| `mobile/` | Мобильное приложение | Expo 57 (React Native) |
| `packages/contracts/` | Общий словарь: описания данных, которыми обмениваются части | Zod (библиотека описания и проверки данных) |

Есть ещё две папки, которые к продукту не относятся и в сборку не входят:
`prototype/` (первая HTML-страница проекта) и `research/`, `design-research/`
(разборы чужих интерфейсов).

## 2. Как части связаны сегодня

Связей меньше, чем частей. Это не упущение — это текущее состояние, и его
надо знать, читая всё остальное.

```
                      packages/contracts
                     (общие описания данных)
                        ▲       ▲       ▲
                        │       │       │
   website ──ссылка──► webapp   │    mobile
   (Astro)   на /app  (React)   │    (Expo)
                        │       │       │
                        └───────┴───────┘
                          пока ходит сюда
                     только шаблонная часть
                                │
                                ▼
                            backend
                        (Hono + Prisma)
```

Что здесь происходит на самом деле:

- **Сайт ведёт в кабинет обычной ссылкой.** Кнопки «Создать агентство»
  и «Войти» на сайте — это `signupHref` и `loginHref` из
  `website/src/lib/site-routes.ts`. Никакого обмена данными между сайтом
  и кабинетом нет: человек просто переходит по адресу.
- **Кабинет разговаривает с сервером только шаблонной своей половиной.**
  Обращения к сети живут в `webapp/src/platform/api/` и используются
  в `features/auth/api.ts`, `features/users/api.ts`, `features/admin/api.ts`.
  Все продуктовые экраны «Сёрчи» — выдача, карточка объекта, баланс,
  подборки, агентство — сети не касаются вовсе.
- **Продукт с бэкендом не разговаривает.** В базе данных сервера нет ни
  объектов, ни объявлений, ни агентств, ни балансов — см. раздел 7.
- **Общий словарь `packages/contracts` подключён ко всем трём приложениям**
  (`@serch/contracts` в зависимостях `webapp`, `mobile`, `backend`), но описывает
  он только то, что умеет сервер: вход, пользователей, покупки в магазинах
  приложений, уведомления.

## 3. Границы: кто за что отвечает

### `website/` — публичный сайт

Статический сайт. «Статический» здесь означает: при сборке каждая страница
превращается в готовый HTML-файл, и на хостинге не нужен работающий сервер —
достаточно раздачи файлов. Это записано прямо в `website/astro.config.mjs`,
там же расписан путь перехода на серверный режим, если он однажды понадобится.

Отвечает за: рассказ о продукте, цены, правовые тексты, страницы собственника
(`/stop`, `/udalit-dannye`, `/podtverdite-nomer`), блог, страницу технических
работ.

Не отвечает за: любые действия внутри продукта. Форм, отправляющих данные,
на сайте нет.

### `webapp/` — кабинет

Одностраничное приложение: браузер загружает один HTML-файл, а дальше экраны
переключает код, не перезагружая страницу. Маршрутизатор — TanStack Router.

Отвечает за: все рабочие экраны агентства и их мобильные версии.

Не отвечает за: хранение данных. Всё, что кабинет показывает, лежит внутри
самого кабинета (раздел 5).

### `backend/` — сервер

Работает на Bun, HTTP-каркас — Hono, доступ к базе — Prisma, база —
PostgreSQL. Точка входа `backend/src/index.ts` поднимает сервер
на `Bun.serve`, приложение собирается в `backend/src/app.ts`.

Отвечает за: вход и сеансы, пользователей и роли, подписки Apple и Google,
push-уведомления.

**Не отвечает ни за что из предметной области «Сёрчи»**: объявлений,
собственников, раскрытий, баланса агентства, отказов, подборок в нём нет.
Подробно — раздел 7.

### `mobile/` — приложение

Expo (React Native) с маршрутизацией `expo-router`. Экраны:
`mobile/src/app/` — вкладки, карточка `details/[id]`, страница оплаты
`paywall.tsx`. Это по-прежнему каркас из шаблона проекта, а не мобильная
«Сёрчь»: мобильные экраны продукта собраны **в кабинете**, под адресами
`/m/…` (раздел 4), а не здесь.

### `packages/contracts/` — общий словарь

Пять файлов: `auth.ts`, `users.ts`, `iap.ts` (покупки в магазинах
приложений), `notifications.ts`, `errors.ts`. Каждый описывает форму данных
на языке библиотеки Zod: какие поля есть, какого они типа, что обязательно.

Зачем: сервер и клиент берут описание из одного места. Если сервер начнёт
присылать не то, клиент это заметит на границе, а не через три экрана.
Проверка описаний живёт в тех же файлах (`auth.test.ts`, `users.test.ts`,
`iap.test.ts`).

Правило зависимостей: пакету разрешено зависеть только от `zod` — это
проверяет `scripts/architecture-check.mjs`.

## 4. Кабинет изнутри

### 4.1. Маршруты — `webapp/src/routes.tsx`

Один файл, 551 строка, и в нём объявлены все адреса кабинета. Адреса делятся
на четыре группы.

**Шаблонные адреса** — то, что досталось от заготовки проекта и умеет
разговаривать с сервером: `/` , `/signup`, `/forgot-password`,
`/reset-password`, рабочее пространство пользователя `/app`, `/app/profile`,
`/app/settings` и администратора `/admin`, `/admin/users`, `/admin/settings`.
Их экраны лежат в `webapp/src/pages.tsx`.

**Стенды** — 27 адресов, начинающихся с `/screen`. Это поверхности для
сверки с макетом: открыть экран рядом с кадром в Pencil и сравнить. Один
из этих двадцати семи — сам `/screen`, карта экранов со ссылками на всё
собранное. Рядом, отдельным адресом, стоит `/kitchen-sink` — полигон
контролов.

**Продуктовые адреса кабинета** — 32 штуки: `/today`, `/search`, `/object`,
`/call`, `/balance`, `/collections`, `/agency/…`, `/dialogs`, `/first-run/…`,
плюс восемь адресов входа (`/register`, `/forgot`, `/confirm-code` и другие).
На них ссылается сайдбар.

**Мобильные адреса** — 54 штуки под `/m/…`. Это **не адаптив**: телефон
в «Сёрчи» — другой набор экранов, а не сжатый десктоп. У него своя нижняя
навигация из пяти вкладок вместо сайдбара, фильтры листом вместо колонки.
Причина отдельных адресов записана в комментарии к `mobileRoutes`: держать
два интерфейса в одном дереве и переключать медиазапросом значит ломать оба
при каждой правке.

Экраны подгружаются по требованию (`lazyRouteComponent`): код экрана
приходит в браузер, когда на экран заходят, а не при первой загрузке.

**Важная особенность, которую надо знать.** Все стенды, продуктовые
и мобильные адреса добавляются в дерево маршрутов только в режиме
разработки — условие `import.meta.env.DEV` в `routes.tsx:486`. В собранном
виде их нет. Это видно и в готовой сборке: в `.demo/app/assets/index-*.js`
дерево маршрутов состоит из пяти корневых адресов плюс два шаблонных
рабочих пространства. Следствие: по опубликованной ссылке кабинет
открывается на шаблонной странице, а вход, который уводит на `/today`
(`auth-screens.tsx:121`), приводит к «страница не найдена». Продуктовый
кабинет сегодня живёт в `bun run dev:webapp`, а не в собранной
демонстрации. Это факт, а не задел на будущее.

### 4.2. Каркас — `features/cabinet/CabinetShell.tsx`

Один каркас несут все экраны продукта. До него он был переписан руками
восемь раз, и правка вроде «Пробный старт вместо баланса» стоила бы восьми
одинаковых правок.

Что внутри каркаса:

| Часть | Файл | Что делает |
|---|---|---|
| `CabinetGuard` | `CabinetGuard.tsx` | Не пускает в кабинет тех, кто не вошёл: отправляет на `/login` |
| `CabinetHeader` | `CabinetHeader.tsx` | Шапка высотой 56: марка, глобальный поиск, баланс, «Пополнить», аватар |
| `CabinetSidebar` | `CabinetSidebar.tsx` | Колонка 240: пять разделов, сохранённые поиски, поиски агентства |
| `CabinetOverlays` | `CabinetOverlays.tsx` | Палитра команд и карта горячих клавиш — обещаны «на любом экране», поэтому висят на каркасе |
| `CabinetPage` | `CabinetShell.tsx` | Колонка содержимого с полями 24 и своей прокруткой |

**Тело каркаса оставлено пустым слотом намеренно.** Экраны делятся на три
вида: с колонкой полей (большинство), без полей вовсе (карточка объекта
с шапкой во всю ширину) и с третьей колонкой фильтров (выдача). Переключатель
на это внутри общего компонента спрятал бы раскладку экрана туда, где её
никто не найдёт, — поэтому колонка вынесена рядом отдельным компонентом
`CabinetPage`.

Про `CabinetGuard` в его же комментарии сказано честно: «он не защищает
данные: за ним нет сервера, и всё, что показывает кабинет, лежит в той же
странице. Это дверь, а не замок, и притворяться замком она не должна».

### 4.3. Разделение на `features/` и экраны

Правило простое: **экран собирает, `features/` предоставляет**.

Экраны лежат прямо в `webapp/src/` отдельными файлами: в 42 файлах корня
`src` объявлено 106 компонентов-экранов. Например `search-screen.tsx` (выдача),
`object-card-screen.tsx` (карточка объекта), `balance-screens.tsx` (баланс),
`mobile-today-screens.tsx` (мобильное «Сегодня»).

`webapp/src/features/` — восемь папок. Каждая отдаёт наружу свои части
через файл `index.ts`, и экран берёт только оттуда:

| Папка | Что отдаёт |
|---|---|
| `cabinet/` | Каркас, шапка, сайдбар, палитра команд, горячие клавиши, мобильные части |
| `listings/` | Всё про объекты: строка выдачи, фото, панель фильтров, отклонение от рынка, чип статуса, пустые состояния, скелет загрузки |
| `agency/` | Части разделов агентства: таблица, полоса уведомления, строка настройки |
| `auth/` | Сеанс и экраны входа — и продуктовые, и шаблонные (раздел 5) |
| `admin/`, `users/`, `navigation/`, `settings/` | Шаблонная часть: администрирование, профиль, навигация по ролям, настройки вида |

Правило «экран не лезет внутрь чужой папки» проверяется автоматически —
`bun run architecture:check` (`scripts/architecture-check.mjs`), там же
ловятся круговые зависимости между папками `features/`.

### 4.4. Откуда берутся данные — `webapp/src/data/`

Два файла, и оба — файлы с данными, а не запросы к серверу.

**`listings.ts`** — 251 объект недвижимости. Собран скриптом
`scripts/generate-listings.mjs` (`bun run listings:generate`) и правится
только им. Медиана цены каждого района сходится с таблицей на лендинге:
сайт обещает «Калининский, медиана 205 тыс ₽/м²», и выдача обязана это
подтверждать, иначе продукт врёт на собственной витрине.

**Телефонов в этом файле нет.** Номер собственника — персональные данные
живого человека. Раскрытие показывает номер, собранный на лету из
идентификатора объекта в коде 900, который операторы связи абонентам
не выдают: позвонить нельзя, а выглядит как обычный
(`features/auth/demo-session.ts`, функция `demoPhone`).

**`search-rows.ts`** — строки выдачи, и их два набора:

- **девять замеренных** (`MEASURED_ROWS`) — сняты с кадра макета до
  последнего слова и несут все восемь состояний объекта разом: в работе,
  стоп-лист, отказ, нет телефона, контакт отозван, прозвонен, раскрыт,
  новый. Такого набора в живой базе может не оказаться неделями, а сверять
  с макетом надо каждый день;
- **все 251** (`ALL_ROWS`) — иначе поиску нечего сужать: на девяти строках
  фильтр по району либо оставляет всё, либо не оставляет ничего.

Стенд `/screen/search` показывает только замеренные, продукт `/search` —
всё. Фильтрация при этом настоящая: табы и чипы районов реально сужают
список, счётчик пересчитывается. Когда за экраном появится сеть, поменяется
источник строк, а не логика.

## 5. Демонстрационный сеанс: вход без сервера

Файл: `webapp/src/features/auth/demo-session.ts`.

**Что это.** Кабинет показывают агентствам до того, как написан сервер.
Человек открывает ссылку, создаёт агентство, заходит и работает — но всё,
что он вводит, живёт в его же браузере, в `localStorage` (хранилище
браузера, переживающее перезагрузку страницы), и никуда не уходит. Ни одна
форма не отправляет данные на сервер, потому что сервера для этого нет.

**Что сеанс помнит:** имя и инициалы, почту, название агентства, роль
(руководитель или агент), остаток на счету, число оставшихся пробных
раскрытий и список адресов, контакты которых уже раскрыты.

**Что сеанс умеет:**

| Действие | Что происходит |
|---|---|
| `signIn` | Вход демонстрационным руководителем. Почта и пароль **не проверяются** |
| `signUp` | Создание агентства: 5 пробных раскрытий, 0 ₽ на счету — ровно то, что обещает лендинг |
| `disclose` | Раскрытие контакта: 199 ₽ либо одно пробное. Повторное раскрытие того же объекта бесплатно — это правило продукта, а не защита от двойного нажатия |
| `topUp` | Пополнение счёта. Деньги приходят сразу |
| `signOut` | Выход |

**Почему вход вообще сделан, а не «пустить всех сразу».** Вход — часть
продукта: агент видит своё имя в шапке, руководитель — своё агентство,
«Выйти» действительно выходит. Демонстрация, где кнопка «Войти» ничего
не меняет, показывает картинку, а не систему.

**Что из этого следует — прямо:**

1. Данные не сохраняются нигде, кроме браузера одного человека. Другой
   браузер, другой компьютер, режим инкогнито — пустой кабинет.
2. Никакой защиты за этим нет. `CabinetGuard` — дверь, не замок.
3. Пароль ничего не значит: любая пара «почта — пароль» пускает внутрь.
4. Приватный режим браузера может запретить запись; тогда сеанс живёт
   до перезагрузки страницы. Это предусмотрено и не ломает работу.
5. Когда сервер появится, менять придётся источник данных, а не экраны:
   экраны берут сеанс через `useSession()` и не знают, откуда он.

**Рядом живёт вторая, шаблонная система входа**, и это сделано осознанно.
`features/auth/api.ts`, `provider.tsx`, `components/LoginForm.tsx`
и остальные умеют разговаривать с бэкендом по-настоящему: регистрация,
вход, обновление сеанса, сброс пароля. Они стоят на шаблонных адресах
`/signup`, `/forgot-password`, `/reset-password`. Комментарий в
`routes.tsx` формулирует это так: «сейчас продуктовый экран красивый
и мёртвый, а шаблонный некрасивый и живой. Меняем их местами тогда, когда
наш научится отправлять форму, а не раньше».

## 6. Сайт изнутри

### 6.1. Страницы

`website/src/pages/` — 18 страниц, каждая отдельным файлом `.astro`. Адрес
страницы равен имени файла: `pricing.astro` открывается по `/pricing`.

Открытые: главная, `/how-it-works`, `/pricing`, `/blog` и одна статья
в нём, `/o-kompanii`, `/kontakty`, `/law`, `/status`, `/oferta`,
`/politika`, `/soglasie`.
Служебные и закрытые от поиска: `/stop`, `/udalit-dannye`,
`/dannye-udaleny`, `/podtverdite-nomer`, `/maintenance`, `/404`.

Общая оболочка документа — `website/src/layouts/BaseLayout.astro`: язык,
заголовок, описание для выдачи, канонический адрес и `robots`. Правило про
`robots` записано в самом файле: `noindex, nofollow` ставится на страницах,
где виден чей-то номер, и это не про трафик, а про 152-ФЗ.

### 6.2. Общие компоненты — `website/src/components/landing/`

26 компонентов, и все 18 страниц собраны из них. Делятся на три вида:

- **обвязка страницы**: `SiteHeader`, `SiteFooter`, `SiteMobileBar`,
  `PublicHeader`, `BrandMark`, `SitePageHero`, `DocPageHeader`;
- **секции**: `HeroSection`, `StatementSection`, `EvidenceSection`,
  `MergeSection`, `StepsSection`, `DistrictsSection`, `PricingSection`,
  `PricePlates`, `FaqSection`, `LegalSection`, `LegalRow`,
  `FinalCtaSection`;
- **мелкие части**: `SiteButton`, `SiteCta`, `SiteFaq`, `PublicAction`,
  `PublicField`, `ListingMock`, `ServicePage`.

Отдельно лежит `website/src/components/ui/` — 60 примитивов shadcn
(кнопки, поля, диалоги и прочее). Это библиотека, копия которой стоит
и в кабинете.

### 6.3. Адреса в одном месте — `website/src/lib/site-routes.ts`

Все адреса сайта заведены **в одном файле**, и шапка с подвалом берут их
оттуда. Причина записана в комментарии и стоила проекту сломанного сайта:
раньше кнопки призыва вели на `/registraciya` — адрес, которого на сайте
нет и не будет, — и в «страница не найдена» вели разом шапка, подвал, герой
главной, три плашки прайса и финальный призыв каждой страницы. Одна строка
ломала весь сайт.

Файл отдаёт:

- `siteRoutes` — адреса страниц;
- `blogPostRoutes` — адреса статей блога;
- `signupHref` и `loginHref` — куда ведут «Создать агентство» и «Войти»;
- `isActiveRoute(pathname, href)` — стоит ли человек сейчас на этой
  странице (нужно, чтобы подсветить пункт меню).

Про `isActiveRoute` стоит знать одну деталь: dev-сервер отдаёт `/pricing`,
а собранный сайт на хостинге — `/pricing/`. Без выравнивания хвостового
слэша пункт меню подсвечивался бы в одном режиме и молчал в другом — причём
именно в том, который видит владелец.

**Куда ведут «Создать агентство» и «Войти».** Адрес кабинета берётся из
переменной окружения `PUBLIC_WEBAPP_URL`. Без неё в разработке
подставляется `http://localhost:5173` — порт, на котором кабинет
поднимается по умолчанию, чтобы кнопка нажималась сразу после
`bun run dev`. В сборке без переменной кабинет ищется в папке `/app` того же
адреса.

**Расхождение, названное вслух и не закрытое.** Часть страниц стоит на
транслитных адресах (`/o-kompanii`, `/kontakty`, `/oferta`), а доска
индексации в макете называет их `/about`, `/contacts`, `/offer`.
Переименование десяти адресов ломает внешние ссылки и требует
перенаправлений — это отдельное решение владельца, а не побочный эффект
починки навигации. Расхождение записано прямо в файле.

### 6.4. Базовый путь для хостинга

Задача: сайт и кабинет должны жить по **одной ссылке** — лендинг на корне,
кабинет в папке `/app`. Человек читает про продукт, жмёт «Создать
агентство» и оказывается в кабинете, не меняя домена.

Сложность в том, что корень адреса бывает разный. На своём домене он
пустой. На GitHub Pages для проекта корень равен имени репозитория:
`…github.io/serch-demo/`. Если этого не учесть, все внутренние ссылки уедут
на корень домена и отдадут чужую страницу — причём заметить это можно
только на хостинге.

Решено одной переменной окружения `SERCH_BASE`:

| Где | Команда | Что получается |
|---|---|---|
| Свой домен | `bun run demo` | сайт на `/`, кабинет на `/app/` |
| GitHub Pages | `bun run demo:pages` | сайт на `/serch-demo/`, кабинет на `/serch-demo/app/` |

Переменную читают три места, и все три обязаны согласоваться:

1. `website/astro.config.mjs` — поле `base`. Astro сам подставит корень
   во все внутренние ссылки;
2. `webapp/vite.config.ts` — поле `base`, собирается как
   `${SERCH_BASE}/app/`. Ошибиться здесь дороже всего: страница откроется
   белой, потому что браузер пойдёт за скриптом не туда;
3. `webapp/src/routes.tsx` — `basepath` маршрутизатора, берётся из того же
   значения (`import.meta.env.BASE_URL`). Без этого маршрутизатор считал бы
   `/app/search` разделом `app`, а не корнем кабинета.

`site-routes.ts` приписывает корень ко всем адресам сайта **в одном
месте** — функция `withBase`.

**Отдельная сложность: глубокие ссылки.** Статический хостинг не знает, что
`/app/search` — это экран, а не файл, и отдаёт страницу «не найдено». Та
возвращает человека в кабинет, приложив исходный адрес параметром `?p=`,
а `webapp/src/deep-link.ts` (подключён первым импортом в `main.tsx`)
забирает адрес обратно в строку браузера **до** того, как маршрутизатор
на неё посмотрит.

**Сборка демонстрации** — `scripts/build-demo.mjs`: собирает сайт, собирает
кабинет, кладёт сайт в `.demo/`, кабинет в `.demo/app/`, дописывает
`.nojekyll` и копию `404.html` для кабинета. Проверяет результат отдельный
скрипт `scripts/check-demo.mjs` (`bun run demo:check`) — он поднимает
сервер, повторяющий поведение GitHub Pages, и обходит все адреса. Заведён
он потому, что сборка бывает зелёной у мёртвого сайта: восемь адресов
из одиннадцати отдавали 404, а сборка, типы и тесты молчали.

## 7. Модули бэкенда

`backend/src/modules/` — четыре модуля.

| Модуль | Что делает |
|---|---|
| `auth` | Регистрация, вход, сеансы, обновление и отзыв токенов, сброс пароля, вход через внешних поставщиков |
| `users` | Профиль, роли, список пользователей для администратора, создание первого администратора при запуске |
| `billing` | Подписки: проверка покупок в App Store и Google Play, приём их уведомлений, состояние подписки |
| `notifications` | Push-уведомления: устройства, очередь отправки, доставка через Expo, политика повторов |

Каждый модуль устроен одинаково и разложен на четыре слоя:

```
modules/<модуль>/
  domain/          правила предметной области, без библиотек
  application/     сценарии: «войти», «сбросить пароль»
  infrastructure/  работа с базой и внешними службами
  transport/       HTTP: адреса, проверка запроса, ответы
  index.ts         единственная дверь наружу
```

Границы слоёв проверяются автоматически: `bun run architecture:check`
запрещает `domain` и `application` знать про Prisma, AWS SDK, `jose` и `pg`,
а модулям — лезть друг другу внутрь мимо `index.ts`. Собирает всё вместе
`backend/src/app.ts`.

Кроме модулей на сервере есть общие службы: `backend/src/storage/` — работа
с объектным хранилищем через AWS SDK, `backend/src/email/service.ts` —
отправка писем (по умолчанию выключена), `backend/src/http/security.ts` —
ограничение частоты запросов и защита входящего трафика.

Запускается сервер тремя разными процессами, и это видно по командам
в `backend/package.json`: `start:api` — сам сервер (`src/index.ts`),
`start:worker` — фоновая обработка очередей (`src/worker.ts`),
`start:cron` — задачи по расписанию (`src/cron.ts`).

Что хранится в базе — видно по `backend/prisma/schema.prisma`. Таблиц
одиннадцать: `User`, `PasswordResetToken`, `AuthSession`,
`SubscriptionEntitlement`, `AppStoreTransaction`, `AppStoreWebhook`,
`GooglePlaySubscriptionPurchase`, `PushToken`, `PushInstallation`,
`PushNotificationOutbox`, `PushDelivery`.

**Продукт с этим сервером пока не разговаривает — и это надо сказать
прямо.** В списке таблиц нет ни объявлений, ни собственников, ни агентств,
ни раскрытий, ни баланса, ни отказов, ни подборок — то есть ничего из того,
чем занята «Сёрчь». Модули умеют пускать человека внутрь и продавать ему
подписку, но им нечего ему показать.

Единственная часть кабинета, которая ходит на сервер, — шаблонная:
`features/auth/api.ts`, `features/users/api.ts`, `features/admin/api.ts`
через `platform/api/http-client.ts`. Адрес сервера берётся из переменной
`VITE_API_URL`, по умолчанию `http://localhost:3000`. Продуктовые экраны
кабинета этот путь не используют вовсе.

Ядро продукта — своя нейросеть похожести, поиск дубликатов объявлений,
определение собственника — в репозитории отсутствует. Этого пока нет.

## 8. Где живёт дизайн-система

Три уровня, снизу вверх.

### 8.1. Токены — `webapp/src/index.css`

«Токен» — именованное значение: не «10 пикселей», а «радиус кнопки». Меняется
в одном месте — меняется везде. Файл на 496 строк, и в нём собрано всё:

| Что задаёт | Как |
|---|---|
| Шрифт | Inter Tight, два начертания — 600 и 500. Третьего нет: иерархия делается кеглем и цветом, не толщиной |
| Кегли | Закрытая лестница из восьми ступеней: 11 · 12 · 13 · 14 · 16 · 20 · 28 · 40. Промежуточных нет; ступени 5xl–9xl обнулены, чтобы их нельзя было применить молча |
| Отступы | База 4 px. Шкала двойная: микро внутри контрола (2…14), макро между блоками (16…140) |
| Радиусы | Привязаны к высоте контрола: 6 · 8 · 10 · 12 · 16 · 24, плюс 2 и 4 для полосок |
| Цвет | Ни синего, ни оранжевого, ни чистого чёрного и белого. Красный в кабинете один и только там, где списываются деньги — с единственным записанным исключением: точка в марке |
| Высоты контролов | Пять ступеней, где высота, радиус и кегль подписи связаны жёстко. Пара «высота с чужим радиусом» — дефект, а не вариант |
| Сетка | Сайдбар 240, шапка 56, содержимое 1152, фильтры 260, выдача 908 |
| Движение | Одна кривая на весь проект, длительность 150 мс. Анимировать разрешено цвет, прозрачность и сдвиг; ширину, высоту и координаты — никогда |
| Плотность | Вариант `compact` переключает высоты и поля ячеек переменными |

Тёмной темы в продукте нет — это записанное решение. В `main.tsx` стоит
`forcedTheme="light"`, чтобы тёмная настройка системы не включила
неопределённые значения в примитивах shadcn.

Шрифт подключён файлами из `webapp/public/fonts`, а не пакетом: путь
до репозитория содержит кириллицу, и Vite в разработке выдавал адрес
в искажённой кодировке — файл не находился, и весь текст молча рисовался
запасным системным шрифтом.

У сайта свой файл токенов — `website/src/styles/global.css` (969 строк),
и лестница кеглей там другая: сайт кричит, кабинет работает.

### 8.2. Типографика — `webapp/src/components/typography.tsx`

Один компонент `Typography` на весь текст продукта. Он не про оформление,
а про роль: `columnHeader`, `metaText`, `denseText`, `uiText`, `strongText`,
`rowPrice`, `panelTitle` и так далее. Кегль, интерлиньяж и разрядка каждой
роли заданы токенами, а не набраны на месте.

Правило закреплено проверкой: собственное правило ESLint
`typographyPolicy/use-typography-component` (`webapp/eslint.config.js`)
запрещает типографические утилиты где-либо, кроме самого `typography.tsx`.

### 8.3. Контролы — `webapp/src/components/controls/`

Пять компонентов: `Button`, `Checkbox`, `TextField`, `FilterChip`,
`SelectChip`. Все значения сняты замером с доски макета `СИСТЕМА · Состояния
контролов`, а не выведены из описания.

Они **собраны заново, а не поверх примитивов shadcn**, и причина названа
в `Button.tsx`: базовый примитив несёт `rounded-md` на всех размерах,
кольцо фокуса в три пикселя, приглушение выключенного прозрачностью, сдвиг
при нажатии и тень. Каждое из этого проект запрещает, а снять снаружи можно
было бы только через `className`, который у закрытых компонентов запрещён.

Рядом лежат `webapp/src/components/ui/` — 60 примитивов shadcn. Они
остаются: их используют шаблонные экраны, и цветовые токены проекта
подставлены в их семантический слой, чтобы не править 70 чужих файлов.

Полигон `/kitchen-sink` показывает все контролы во всех состояниях —
это поверхность для сверки с доской, а не страница продукта.

## 11. Чего в архитектуре пока нет

Список честный и без «скоро».

1. **Связи продукта с сервером.** Кабинет «Сёрчи» не отправляет и не
   получает ни одного запроса. Обращения к сети есть только у шаблонной
   половины кабинета.
2. **Предметной области на сервере.** В базе нет объявлений, собственников,
   агентств, балансов, раскрытий, отказов, подборок.
3. **Сбора объявлений.** Ни одного источника данных, ни одного парсера,
   ни одного расписания в репозитории нет.
4. **Нейросети похожести.** Ядро продукта — определение собственника
   и склейка дублей — не начато.
5. **Настоящей защиты кабинета.** `CabinetGuard` — дверь, не замок; пароль
   не проверяется.
6. **Мобильного приложения «Сёрчи».** `mobile/` — каркас из шаблона.
   Мобильные экраны продукта собраны в кабинете под `/m/…`.
7. **Продуктовых адресов кабинета в собранном виде.** Они добавляются
   в дерево маршрутов только в режиме разработки (`routes.tsx:486`).
8. **Остальных документов в `docs/`.** `CLAUDE.md` и `AGENTS.md` ссылаются
   на `docs/LOCAL_DATABASE.md`, `docs/TESTING.md`, `docs/DEPLOYMENT.md`,
   `docs/STORAGE.md` — их стёрла та же сборка, и они не восстановлены.
   Сегодня README лежат рядом с частями: `backend/README.md`,
   `webapp/README.md`, `website/README.md`, `mobile/README.md`,
   `packages/contracts/README.md`, `webapp/design-check/README.md`.
