# База данных

Кабинет умеет работать двумя способами, и переключается это **одной парой
значений**, а не флагом в коде.

| Где | Что за хранилище | Что работает |
|---|---|---|
| Демонстрация на GitHub Pages | браузер посетителя | всё однопользовательское |
| Рабочая версия | Supabase (PostgreSQL) | всё, включая ссылку клиенту и общую работу агентства |

Заданы `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` — работаем с базой.
Не заданы — с браузером. Ни одного `if` про «демо» в экранах при этом нет:
экраны не знают, откуда пришли данные.

---

## Что не работает без базы

Не «работает хуже», а **не может работать в принципе**. Чужой браузер не видит
хранилище вашего, и никакая хитрость это не обходит.

- **Ссылка на подборку у клиента.** Клиент открывает её на своём телефоне.
- **Общие поиски агентства.** «Общее для всех сотрудников» в браузере одного
  человека существовать не может.
- **«Коллега уже звонил».** Пока журналы у каждого свои, два агента звонят
  одному собственнику, и агентство получает жалобу.
- **Вход с другого устройства.** Без базы вход находит агентство, заведённое
  на этом же компьютере.

## Поднять базу у себя

Нужен Docker Desktop — запущенный, а не просто установленный.

```
npx supabase start
```

Первый запуск качает около двух гигабайт образов и идёт минут десять.
В конце команда печатает значения; нужны два:

```
API_URL   → VITE_SUPABASE_URL
ANON_KEY  → VITE_SUPABASE_ANON_KEY
```

Положите их в `webapp/.env.local` (образец — `webapp/.env.local.example`)
и перезапустите сервер разработки.

Полезное рядом:

| Команда | Что делает |
|---|---|
| `npx supabase status` | адреса и ключи поднятой базы |
| `npx supabase stop` | остановить, данные остаются |
| `npx supabase db reset` | пересоздать базу с нуля по миграциям |
| `http://127.0.0.1:54323` | Studio: таблицы и содержимое глазами |
| `http://127.0.0.1:54324` | почта, которую отправляет вход |

## Переехать в облако

1. Завести проект на supabase.com (вход через GitHub, карта не нужна).
2. `npx supabase link --project-ref <идентификатор проекта>`
3. `npx supabase db push` — миграции уезжают в облако.
4. Взять `Project URL` и `anon key` из настроек проекта и положить
   в `webapp/.env.local`.

**Ключ `service_role` не кладётся никуда**, что уезжает в браузер. Он обходит
все правила доступа целиком.

---

## Почему открытый ключ — это нормально

`anon key` виден любому, кто откроет исходники страницы. Это не утечка:
ключ говорит «я это приложение», а не «я такой-то человек».

Кто пришёл — решает сеанс входа. Что ему можно — решают правила внутри базы
(row level security). Экран можно обойти через консоль браузера за минуту;
правило базы обойти нельзя, потому что оно применяется на сервере к каждому
запросу.

Поэтому все запреты продукта живут в миграции, а не в коде экранов.

---

## Что кому видно

Правила описаны в `supabase/migrations/20260807122001_workspace.sql`
и проверяются `webapp/tests/access-rules.test.ts` — настоящими запросами
от двух настоящих агентств, а не чтением SQL глазами.

| Кто | Что видит |
|---|---|
| Сотрудник агентства | всю работу СВОЕГО агентства и ничего чужого |
| Клиент по ссылке, без входа | подборку с включённой ссылкой и её состав |
| Он же | НЕ видит: раскрытия, деньги, сотрудников, другие подборки |

Три правила стоят отдельно, потому что это решения продукта, а не техники:

**Агентство подставляет база, а не браузер.** Ни один запрос не присылает
`agency_id` сам — его вычисляет функция `my_agency_id()`. Присланное поле
можно подменить из консоли; вычисленное базой нельзя.

**Отметка «просил не звонить» не удаляется.** Ни агентом, ни руководителем,
ни нами. Запрет стоит дважды — нет права `delete` и нет политики `delete`, —
и снятие любого поодиночке ничего не откроет. Чтобы разрешить снимать отказы,
придётся сознательно править два места.

**Гость закрыт двумя слоями, а не одним.** Облако выдаёт права на новую
таблицу автоматически — это его правило по умолчанию, и первая миграция
его не учла. Данные при этом не утекали: отбор строк гостя не пускал.
Но защита держалась на одном слое, а одной ошибки в одном правиле хватило
бы, чтобы открылась вся таблица. Вторая миграция отзывает права прямо
и выключает правило по умолчанию, чтобы история не повторилась на первой
же новой таблице.

**За один объект агентство платит один раз.** Это ограничение таблицы
(`unique (agency_id, address)`), а не проверка на экране: два экрана, нажатые
одновременно, иначе спишут дважды.

## Как устроено в коде

```
webapp/src/platform/db/          подключение: клиент и «настроена ли база»
webapp/src/features/auth/remote  вход, регистрация, кто вошёл
webapp/src/features/workspace/   журналы: что записываем и что читаем
  ├── store.ts                   память кабинета, одна на оба хранилища
  └── remote.ts                  тот же журнал на сервере
supabase/migrations/             схема и правила доступа
```

**Запись не ждёт сервера.** Раскрытие, звонок, добавление в подборку
происходят в памяти сразу, а на сервер уезжают следом: агент делает
тридцать-пятьдесят таких действий за смену, и ожидание сети на каждом
превращает продукт в анкету.

**Но потеря не бывает молчаливой.** Если запись не доехала, человек видит
сообщение. Журнал, по которому считают деньги, не имеет права терять строки
тихо: агентство узнало бы об этом на сверке через месяц.

**Чтение наоборот: сервер сильнее браузера.** Кабинет открывается тем, что
лежит рядом, — мгновенно, без пустого экрана, — а следом приезжает правда
с сервера и замещает её. Браузер знает только работу этого человека на этом
устройстве; сервер знает работу всего агентства.

---

## Чего пока нет

- **Слияния расхождений.** Двое правят одну подборку — побеждает последний.
- **Приглашения сотрудника письмом.** Строка в `people` заводится, а письма
  нет: нужен почтовый сервис, а не база.
- **Списаний за подписку.** Журнала подписки в базе нет, поэтому вкладка
  актов пуста.
