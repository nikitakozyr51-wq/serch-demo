# Семь мёртвых кнопок — разбор с двух сторон

Записано 7 августа 2026. Ответ на отчёт чата разработки: «перепись 30 экранов,
0 ошибок, 7 мёртвых узлов».

Проверено с обеих сторон: что есть в Pencil и что есть в `webapp/src`.
Ссылки на код — `файл:строка`, не пересказ.

---

## Сначала о самой переписи, потому что это важнее семи кнопок

**Перепись считает кнопку живой, если у неё есть атрибут `data-action`.**

`scripts/find-dead-buttons.mjs:106`

```js
const live =
  HANDLERS.some(has) ||
  SPREAD.test(props) ||
  has('data-action') ||      // <- вот эта строка
  ...
```

Атрибут `data-action` **не читается нигде**: во всём `webapp`, `scripts` и
`tests` нет ни одного `dataset.action` и ни одного селектора `[data-action]`.
Это описательная пометка, а не поведение.

Проверка числом — перепись прогнана дважды, со строкой 106 и без неё:

| | Подозрительных узлов |
|---|---|
| как есть | **15** |
| без строки 106 | **56** |

**Атрибут выводит из-под счёта 41 кнопку без обработчика.** Всего помечено 71
кнопка; часть из них живая по-настоящему (у них есть и `onClick`, и пометка),
но сорок одна — нет.

Отсюда следует, что «24 → 7» описывает не число мёртвых кнопок, а число
**непомеченных** мёртвых кнопок. Семь оставшихся — те, до которых пометка
не дошла.

Это тот же класс дефекта, о котором `DESIGN.md` предупреждает про слои
проверки: **проверку сделали зелёной, а не работу — рабочей.** Пометка
описывает намерение, а перепись принимает намерение за исполнение.

**Что делать:** убрать `data-action` из списка признаков живого. Тогда число
станет честным — 56 — и его можно будет уменьшать работой. Пометку как
документацию оставить не жалко, но она не должна закрывать глаза счётчику.

сегодня.

|---|---|---|
| Список пополнений | `БАЛАНС · Пополнения` есть | **маршрут** |
| Пригласить агента | `КАБИНЕТ · Пригласить агента` есть | **маршрут**, дальше бэкенд |

### 1. Список пополнений

Данные есть и грузятся: `Workspace.topUps` (`features/workspace/store.ts:200`),
загрузка с сервера (`features/workspace/remote.ts:141`). Мобильный экран
работает: `mobile-balance-screens.tsx:564`.

Не хватает **десктопного маршрута** `/balance/top-ups` — в `routes.tsx:481`
его нет, хотя пара `["/balance/top-ups", "/m/balance/top-ups"]` уже объявлена
в `features/cabinet/platform.ts:53`.

Вкладка поэтому рендерится как `<button>` без адреса
(`balance-screens.tsx:307`), а `onTabSelect` до неё не доходит: единственная
страница, которая его передаёт, подставляет свой набор вкладок
(`balance-screens.tsx:722`).

Сборки строк на десктопе тоже нет — на мобиле это `topUpRows`
(`mobile-balance-screens.tsx:542`), на десктопе только `documentsOf`, которая
превращает пополнения в документы.

### 2. Пригласить агента

Кнопка без обработчика, `agency-staff-screen.tsx:130`. Маршрута
`/agency/invite` нет; существующий `/invite` — это **приём** приглашения
получателем (`auth-more-screens.tsx:202`), а не отправка.

Мобильная форма нарисована, но её поля неуправляемые — без `value`/`onChange`,
без `<form>` (`mobile-agency-people-screens.tsx:406`).

Глубже: **приглашений нет в бэкенде вовсе.** Ни таблицы, ни функции
в `supabase/migrations`, ни одного вызова API. Из RPC есть только
`create_agency` и `my_agency_id`.

### 3. Изменить реквизиты

Кадр есть, маршрута нет. И хранить негде: `public.agencies`
(`supabase/migrations/20260807122001_workspace.sql:36`) держит только
`id, name, created_at, balance, trial` — колонок ИНН, КПП и адреса нет.

ИНН, который человек вводит при регистрации, **выбрасывается**: `signUp`
принимает только имя, почту, агентство и пароль.

### 4. Передать роль

Кадр есть, экрана выбора сотрудника и маршрута нет. Колонка `role` у `people`
уже существует — значит после экрана нужен только путь записи. Сейчас его нет:
в `features/workspace/remote.ts` для `people` есть только `insert`, нет
`update`; в `store.ts` нет ни `transferOwner`, ни `setRole`.

### 5. «Применить ко всем» — не про лимит

**Поправка к формулировке отчёта.** Кнопка стоит в строке
**«Вид по умолчанию для агентства»** (`агентство → настройки`), а не
в дневном лимите. Дневной лимит по умолчанию — соседняя настройка, и она
подписана «применяется к новым сотрудникам»: раскатки на существующих
у лимита нет **намеренно**, существующим меняют по одному в карточке.

А вот вид действительно раскатывается на всех, и подтверждения к этому
не было. **Нарисовано: `СОСТОЯНИЕ · Поставить вид всем`.**

Почему подтверждение, а не молчаливое применение с отменой: действие меняет
**чужие экраны**, а прежние значения не сохраняются — отменить нечем.
Диалог называет число, поимённо перечисляет, кого касается, и говорит прямо,
что вернуть можно только вручную:

> **Поставить всем плотный вид?**
> Плотность и набор полей заменятся у четверых сотрудников. Свой выбор
> каждого не сохраняется: вернуть прежнее можно только вручную, по одному.
> Лебедев Максим · Титова Анна · Гусев Пётр · Королёв Дмитрий

Мобильной пары нет и не нужно: на `МОБАЙЛ · Настройки агентства` этой
настройки не существует, раскатка — действие руководителя за столом.

### 6. Запросить удаление агентства

Кадр есть, диалога и маршрута нет. Самое необратимое действие продукта
сознательно оставлено без обработчика до появления экрана — это правильное
решение, а не забывчивость.

API удаления тоже нет: в `features/auth/remote.ts` экспортируются только
`loadIdentity`, `setBalance`, `signInRemote`, `signOutRemote`, `signUpRemote`.

### 7. Изменить адрес в фильтрах

Десктопного кадра не было вовсе — только `МОБАЙЛ · Рядом с адресом`.
Поэтому проп `onChangeAddress` объявлен в `FilterPanel.tsx:123` и не
передаётся ни одним из двух вызывающих.

**Нарисовано: `СОСТОЯНИЕ · Рядом с адресом`** — десктопный близнец мобильного
листа, содержимое перенесено дословно: поле адреса линией снизу, радиус
чипами 500 м · 1 км · 2 км, объяснение про сложение фильтров, кнопки
«Убрать ограничение» и «Показать 247 объектов».

У каждого мобильного листа в файле есть десктопный диалог-близнец. У этого
не было — единственное исключение из полной пары, то есть недосмотр,
а не решение.

Данных под него пока нет: сохраняемый фильтр содержит только `districts`,
`rooms`, `priceCap`, а источника подсказок в проекте нет ни одного —
ноль совпадений по `suggest`, `autocomplete`, `geocode`, `dadata`.

## Порядок, в котором это дешевле делать

1. **Убрать `data-action` из признаков живого** и посмотреть на честное
   число. Одна строка.
2. **Четыре маршрута и экрана** — пополнения, приглашение, реквизиты,
   передача роли. Кадры есть, рисовать нечего.
3. **Диалог удаления агентства** — кадр есть.
4. **Два новых кадра** — адрес и раскатка вида — развести по коду.
5. **Бэкенд** — приглашения, колонки реквизитов, запись роли, удаление.
   Это самая долгая часть, и она не зависит от дизайна.

Дизайн после сегодняшнего не блокирует ни одну из семи.
